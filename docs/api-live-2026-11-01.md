# Astra Cockpit API — Live Recheck 2026-11-01

This document records the protocol and payload shapes observed on
2026-11-01 against the tenant account used for this integration. It is a
reverse-engineering note, not an official Astra specification.

Sensitive values are synthetic or described structurally. Raw captures remain
local, are gitignored, and must not be committed.

Related documents:

- [api.md](api.md): earlier static analysis and web observations
- [openapi-astra-android.yaml](openapi-astra-android.yaml): machine-readable mobile schema
- [openapi-web-observed.yaml](openapi-web-observed.yaml): observed web endpoints

## 1. Login Scheme

### Mobile API

Both mobile clients use one signed form endpoint:

```text
POST https://astra-cloud.com/readyxnet/source/login/csandroid.php   (Android)
POST https://astra-cloud.com/readyxnet/source/login/csios.php        (iOS)
Content-Type: application/x-www-form-urlencoded
```

Every request contains `s_dv=1`. The response is the JSON payload followed by
`md5(payload)` as the final 32 hex characters. A client must strip and verify
that suffix before parsing.

The login identity is the **full email address** registered with Astra Cockpit.
The observed account rejected a short tenant name, an upper-cased email address
and an email address with trailing whitespace. The password is used unchanged.

```text
password_hash = md5(password)
s_sid         = md5(email + password_hash)
```

The login sequence is:

1. Fetch a timestamp:
   - `s_action=get_ts`
   - `s_ts=`
   - `s_cs=md5("SNAFU" + "get_ts" + "")`
2. Call the action:
   - `s_action=auth_login`
   - `s_ts=<timestamp response>`
   - `s_cs=md5("SNAFU" + action + timestamp)`
   - `s_sid=<session id>`
   - `s_immo=-1`
   - `s_year=<YYYY>`
   - `s_med=1`
   - `s_lang=de`
   - `s_mnt=-1`
   - `s_datum=-1`

`auth_login` returns `auth: "1"`, `immo_sel`, the account metadata and an
additional `data[]` array containing the same six current-year overview rows
that `get_mtr_vb_overview` returns. The integration consumes those rows once
for the first refresh and then uses the dedicated endpoint.

### Empty HTTP 200 and IP Filtering

The same `get_ts` request was observed to return:

```text
HTTP/1.1 200 OK
Content-Length: 0
Connection: close
```

from one residential egress IP after repeated probing. The identical request,
with the same account and password, returned a valid timestamp from a different
egress IP at the same time. This is provider-side deferral, rate limiting or IP
filtering. It is **not** evidence of invalid credentials.

The integration classifies an empty/truncated response as
`AstraDeferredDataError`, backs off, keeps the last safe values, and can use the
browser/recorder fallback. Only an explicit `auth: "0"` (or an authentication
rejection message) triggers reauthentication.

If the integration reports `deferred` or `empty_html`, check the diagnostics
instead of repeatedly changing the password:

- `sensor.astra_api_status`
- `sensor.astra_response_class`
- the `Astra Energy data deferred` repair issue

### Web Portal

There are three browser login entry points, all sharing
`login.js?v=1.6`:

| Portal | Login page | `g_sys` | `strRequestType` |
| --- | --- | --- | --- |
| Astra Cockpit | `/readyxnet/source/login/csloginw.php` | 1 | `Submit` |
| Energy Monitoring | `/readyxnet/source/login/csloginem.php` | 2 | `submit_login` |
| Inventory | `/readyxnet/source/login/csloginiv.php` | 3 | `submit_login` |

The current login form contains:

- visible `UserName` and `Password` inputs
- a hidden-by-CSS `Email` input
- hidden `bActivationFlag=NOCHECK`, `iCounter=0`, `strRequestType`,
  `userEULA`, `EULA_OK=0`
- hidden `g-recaptcha-response`
- an **image submit control** (`input[type=image]`), not a submit button

The page loads reCAPTCHA v3 with site key
`6LdWT-AZAAAAAA4XSFlDy4EL6k-TPw-ibrptnsy7`. The JavaScript calls
`grecaptcha.execute(..., {action: "login"})`, writes the token into
`g-recaptcha-response`, and submits the form. Direct HTTP login without a valid
reCAPTCHA token returns the login page again. A real browser is therefore
required unless Astra disables reCAPTCHA for the deployment.

The browser-proxy autofill now fills `#UserName` and `#Password` and clicks
`input[type=image]`; this fixes the previous behavior where the form was filled
but never submitted. Interactive CDP login is still required when Astra shows a
challenge.

## 2. Action Catalogue

All data actions use the common parameters:

| Parameter | Meaning |
| --- | --- |
| `s_sid` | `md5(email + md5(password))` |
| `s_immo` | Selected location id, initially `-1`, then `immo_sel` (`4^...` in the observed account) |
| `s_year` | Selected year, `YYYY` |
| `s_med` | Medium id; `1` = Strom |
| `s_lang` | `de` |
| `s_mnt` | Selected month; `-1` for default/all |
| `s_datum` | `-1` for default/all, or `YYYY-MM-DD` for a daily view |
| `s_dv` | Always `1` |

| Action | Purpose | Notes |
| --- | --- | --- |
| `auth_login` | Authenticate and bootstrap account | Returns metadata, locations, media and current overview rows |
| `get_mtr_lzs` | Latest meter stands | 3 rows for total, T1 grid and T2 solar/object |
| `get_mtr_vb_overview` | Current-period overview metrics | 6 key/value/unit rows |
| `get_mtr_eb` | Energy balance | Monthly chart plus optional daily/hourly/15-minute series |
| `get_mtr_vbmed` | Consumption by medium | Monthly chart plus optional daily/hourly/15-minute series |
| `get_mtr_hist` | Historical comparison | 24 hourly average profiles |
| `get_mtr_autarkie` | Autarky card | Three channels for the selected period |
| `get_mtr_verbrauch` | Monthly consumption series | Current and previous year |
| `get_verbrauch` | Non-tenant monthly consumption | Current and previous year as list-of-dicts |
| `get_mtr_inv` | Invoices and payments | Invoice list plus document handles |
| `get_mtr_inv_pdf` | Invoice PDF metadata | `s_id` is the document `url` handle |
| `get_immo_list` | Selected location list | 5 entries in the observed account |
| `lngchg_medium_list` | Medium list after language change | Same shape as `med_list` |
| `get_wf` | Weather forecast card | Can return empty strings |

`get_mtr_inv_pdf` is the only action that does **not** use the common parameter
set. It sends only `s_sid` and `s_id`, plus the signed request header:

```text
s_action=get_mtr_inv_pdf
s_ts=<timestamp>
s_cs=md5("SNAFU" + "get_mtr_inv_pdf" + timestamp)
s_sid=<session id>
s_id=<document url handle>
s_dv=1
```

## 3. Payload Shapes

### `get_mtr_lzs`

Top-level: `auth`, `data[]`.

| Field | Observed meaning |
| --- | --- |
| `v01` | Meter identifier/label, for example `<meter-id>/0`, `ZT1_<id>/0`, `ZT2_<id>/0` |
| `v02` | Cumulative meter stand in `v03`; lifetime counter, including prior years |
| `v03` | Unit, normally `kWh` |
| `v04` | Consumption for the selected period: current year by default, month with `s_mnt`, day with `s_datum` |
| `v05` | Reading date, `DD.MM.YYYY` (provider-local) |
| `v06` | Channel label: `Strom VGB`, `Strom T1 (Netzbezug)`, `Strom T2 (Objektbezug)` |
| `v07` | Account/order label |

Observed grouping:

- physical/VGB row: total cumulative energy and raw meter id
- T1 row: raw grid import
- T2 row: solar/object energy

The provider's total is not always exactly `T1 + T2`; the integration derives
grid import as `total - solar` and keeps raw T1 separately for diagnostics.

### `get_mtr_vb_overview`

Top-level: `auth`, `data[]`; each row has `v01` (metric key), `v02` (value),
`v03` (unit).

| Metric key | Meaning |
| --- | --- |
| `str_mtr_vbo_vb_strom_gesbez` | Total electricity for the selected period |
| `str_mtr_vbo_vb_strom_t1` | Raw grid/T1 electricity |
| `str_mtr_vbo_strom_t2` | Solar/object/T2 electricity |
| `str_mtr_vbo_vb_strom_pv` | PV electricity; observed equal to T2 |
| `str_mtr_vbo_vmco_strom_pv` | Avoided CO2 in tonnes |
| `str_mtr_vbo_autarkiegrad` | Autarky percentage |

With `s_datum=YYYY-MM-DD`, the observed response populated only the total row
and returned zero for T1/T2/autarky. Use `get_mtr_eb` for the daily split.

### `get_mtr_eb`

Top-level: `auth`, `data[]`; normally one object with chart fields.

Channel families:

| Prefix | Series title | Observed channels |
| --- | --- | --- |
| `_lvb` | Combined balance | `Gesamtbezug,Netzbezug,Objektbezug,PV-Bezug,Batterie-Bezug` |
| `_vb` | Grid/object/battery | `Netzbezug,Objektbezug,Batterie-Bezug` |
| `_vbt2r` | Tariff split | `Netzbezug,Objektbezug` |
| `_lt2rvb` | Tariff split with total | `Gesamtbezug,Netzbezug,Objektbezug` |
| `_ez` | PV delivery | `PV-Netzlieferung,Batterie-Ladung,PV-Objektlieferung` |
| `_lez` | PV delivery with total | `PV-Gesamtlieferung,PV-Netzlieferung,Batterie-Ladung,PV-Objektlieferung` |

Each family has these field variants:

| Suffix | Meaning |
| --- | --- |
| `_ttl` | Comma-separated channel titles |
| `_clr` | Comma-separated chart colors |
| `_eh` | Unit, normally `kWh` |
| `_lbl` | 12 monthly labels (`Jan`…`Dez`) or 24 hourly labels (`01:00`…`00:00`) for a daily request |
| `_lbl_14h` | 96 interval-end labels (`00:15`…`00:00`) for a daily request |
| `_lblsize`, `_lblsize_14h` | Preformatted label variants used by the app chart |
| `_lblsm`, `_lblsm_14h` | Chart label-size hints |
| `_vll` | Semicolon-separated channel series; each channel has 12 monthly or 24 hourly values |
| `_vll_14h` | Semicolon-separated channel series; each channel has 96 quarter-hour values for a daily request |

Daily 15-minute semantics:

- labels are provider-local `Europe/Berlin` **interval ends**
- one value is interval energy in kWh
- average power in kW is `interval_kwh * 4`
- `Netzbezug = max(Gesamtbezug - Objektbezug or PV-Bezug, 0)` in observed data
- `Batterie-Bezug` was zero for the observed account

### `get_mtr_vbmed`

Top-level: `auth`, `data[]`; one object.

| Prefix | Channels |
| --- | --- |
| `_hvb` | `Gesamtbezug,Netzbezug,Objektbezug,PV-Bezug,Batterie-Bezug` |
| `_hvbt2r` | `Gesamtbezug,Netzbezug,Objektbezug` |
| `_hvbc` | `Netzbezug,Objektbezug,Batterie-Bezug` |
| `_hvbct2r` | `Netzbezug,Objektbezug` |
| `_vb` | `Gesamtbezug,Netzbezug,Objektbezug,PV-Bezug,Batterie-Bezug` |

The `_hvb`/`_hvbt2r` families are the useful ones for monthly consumption and
the observed current-month split. `_hvbc` and `_hvbct2r` were zero for the
observed account.

### `get_mtr_hist`

Top-level: `auth`, `data[]`; one object.

- `_lvb_ttl`: `Gesamt,Sommer (April - September),Winter (Oktober - März),Wochentage,Wochenenden`
- `_lvb_vll`: five comma-separated 24-value hourly profiles
- `_lvb_lbl`: 24 hourly labels
- `_lvb_clr`, `_lvb_eh`: colors and unit

These are comparison profiles, not cumulative Energy Dashboard totals.

### `get_mtr_autarkie`

Top-level: `auth`, `data[]`; one object.

- `_lvb_ttl`: `Netzbezug,PV-Bezug,Batterie-Bezug`
- `_lvb_vll`: three comma-separated values in kWh for the selected period
- `_lvb_eh`: `kWh`

### `get_mtr_verbrauch`

Top-level: `auth`, `data[]`; one object.

| Field | Meaning |
| --- | --- |
| `_vb_ttl` | Comma-separated years, for example `2025,2026` |
| `_vb_vll_vy` | Current-year monthly values, 12 comma-separated numbers |
| `_vb_vll_ly` | Previous-year monthly values, 12 comma-separated numbers |
| `_vb_x` | Month numbers `1`…`12` |
| `_vb_eh` | Unit, normally `kWh` |

### `get_verbrauch`

Top-level: `auth`, `vb_eh`, `vb_leg[]`, `vb_ly[]`, `vb_vy[]`, `vb_x[]`.

Each of `vb_ly`, `vb_vy`, `vb_x` is a list containing one object with
`v01`…`v12`. `vb_leg` is a list of `{VJ, LJ}` year labels.

### `get_mtr_inv`

Top-level: `auth`, `data[]`.

Each row:

| Field | Meaning |
| --- | --- |
| `TITEL` | Invoice category, for example rent-electricity or heating-cost invoice |
| `DATUM` | Payment status text, for example last payment date |
| `SUM` | Display total, for example `123,45 EUR` |
| `DOCS` | Encoded documents; see below |

Current `DOCS` encoding observed on 2026-11-01:

```text
key=value;key=value;...:key=value;key=value;...
```

- documents are separated by `:`
- fields inside one document are separated by `;`
- observed keys: `Nummer`, `Datum`, `Betrag`, `Fälligkeit`, `bezahlt am`, `url`
- the `url` value is the handle for `get_mtr_inv_pdf`

The Android 1.0.14 parser expected six positional fields
(`Nummer;Datum;Betrag;Fk;Bez;Url`) rather than key/value pairs. Do not copy
that parser blindly; prefer key/value parsing and keep unknown keys.

### `get_mtr_inv_pdf`

Top-level: `auth`, `data[]`; one object with `pdfUri` and `alias`.

The app builds the document URL as:

```text
https://astra-cloud.com/{alias}/readyxnet/source/userdocs/{pdfUri}
```

### `get_immo_list` and `lngchg_medium_list`

- `get_immo_list`: `auth`, `standort_list[]` with `id`, `name`, `country`
- `lngchg_medium_list`: `auth`, `med_list[]` with `id`, `img`, `name`

### `get_wf`

Top-level: `auth`, `data[]`; one weather card object with:

`_vll1`…`_vll6`, `_lbl6`, `_ttl1`, `_ttl1_1`, `_ttl2`…`_ttl6`.

The observed account returned empty strings for all weather fields.

## 5. Integration Mapping

| Integration field | Source |
| --- | --- |
| `total_kwh` | `get_mtr_lzs` physical/VGB row `v02` |
| `solar_kwh_total` | T2/object/PV row `v02` |
| `grid_kwh_total` | `total - solar`, with raw T1 kept for diagnostics |
| `raw_grid_kwh_total` | T1 row `v02` |
| `current_year_*` | `auth_login.data[]` first, then `get_mtr_vb_overview` |
| `current_month_*` | `get_mtr_vbmed` `_hvb_vll` / `_hvbt2r_vll` at the current month index |
| `autarky_percent` | `str_mtr_vbo_autarkiegrad` |
| `pv_co2_savings_t` | `str_mtr_vbo_vmco_strom_pv` |
| 15-minute backfill | `get_mtr_eb` `_lvb_vll_14h`, provider-local interval ends |

Home Assistant long-term statistics require top-of-hour timestamps, so the
quarter-hour backfill selects hourly rows from the 15-minute source. The local
CSV export tool keeps the full 15-minute resolution.

## 6. Reproduction Commands

Use local, gitignored credentials only:

```sh
cp .env.example .secrets.env
# set ASTRA_USERNAME to the full email address and ASTRA_PASSWORD

python3 tools/astra_mobile_probe.py
python3 tools/astra_raw_dump.py --out captures/astra-raw-live.json
python3 tools/astra_raw_dump.py \
  --date 2026-10-31 \
  --actions get_mtr_eb,get_mtr_vbmed,get_mtr_lzs,get_mtr_vb_overview,get_mtr_autarkie,get_mtr_hist \
  --out captures/astra-raw-day.json
```

If `get_ts` returns an empty 200, wait for the integration's backoff and retry
from a different egress IP. Do not paste raw captures into issues.
